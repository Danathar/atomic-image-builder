Maintenance Notes
=================

Fedora Atomic Fallback Tag
--------------------------
FEDORA_ATOMIC_FALLBACK_TAG in atomic_image_builder.py is the default Fedora
version used for Fedora Atomic base images (Silverblue, Kinoite, etc.) when the
tool cannot detect the host's Fedora version.

The detection works like this:
- On a Fedora system, the tool reads VERSION_ID from /etc/os-release and uses
  that directly.  When the user upgrades to a new Fedora release, the tool
  picks it up automatically.
- On non-Fedora systems (Ubuntu, macOS, containers without os-release), the
  tool falls back to FEDORA_ATOMIC_FALLBACK_TAG.

Universal Blue images are unaffected — they use :stable, which floats
automatically.

Action required: when a Fedora release goes EOL, bump FEDORA_ATOMIC_FALLBACK_TAG
to the current stable Fedora version.  This is a one-line change.  The
maintenance audit (maintenance_audit.py) is the right place to add a check for
this if desired.

Workflow Patcher Indentation Sensitivity
----------------------------------------
patch_workflow_signing_steps, ensure_workflow_job_env_entries, and the per-line
patch_container_workflow / patch_bluebuild_workflow helpers in
atomic_image_builder.py all depend on the exact indentation used by the bundled
template snapshots (2-space step items; 4-space env:/steps: anchors; 6-space
job-env entries).  ensure_workflow_job_env_entries defines a variable in
each job that reads it (a line referring to env.<NAME>), never in "the first
job": job env does not cross jobs, and a guard in build_push testing a variable
defined in an owner's earlier lint job is false forever -- the silent-unsigned
outcome (#344).  When the reading job has no env:/steps: anchor at the expected
indentation it raises CommandError rather than returning the text unchanged,
because that no-op is exactly the failure this section warns about.  When no
job reads the variable it does nothing, which is the shape of a workflow whose
owner removed the signing steps.  Indentation is the only thing it is strict
about within a job: the presence check is by key name among the 6-space
entries directly under the job's env: block, so an owner's differing value or
trailing comment counts as defined and is left alone, and the env:/steps:
anchors tolerate an inline comment.  The alternative was a duplicate mapping
key, which GitHub refuses to parse (#345).  An env: that already carries an
inline value (env: { FOO: bar }) cannot take nested entries; that shape raises
CommandError rather than writing a second env: key into the same job.

The paths-ignore state-file entry is the exception to "no match, no change":
it is inserted as a new sequence item, so a shape mismatch corrupts the file
rather than leaving it alone.  A managed repository may write the list inline
("paths-ignore: ['**.md']"), where a block "- item" beneath it is a parse
error and GitHub runs nothing from the workflow.  Both patchers therefore go
through extend_flow_sequence_line first, which extends an inline list in place
(keeping a trailing comment, and not doubling a trailing comma) and returns
None for the block form — see #358.

The one place a mismatch corrupts output rather than no-op'ing is the
paths-ignore state-file entry: it is inserted as a new sequence item, and an
item at the wrong indent makes the whole sequence unparseable.  Both patchers
therefore copy the indent of the first existing entry (block_sequence_entry_indent)
and only assume key indent plus two for an empty list — see #359.

maintenance_audit.py currently validates action pin coverage but does not run
the patchers against the snapshots.  When refreshing a template snapshot, run
the test suite — the golden-file patcher tests in
tests/test_atomic_image_builder.py cover the current shape.  Add a round-trip
audit here if upstream ever changes the indentation style; the silent no-op
failure mode is hard to notice otherwise.

Third-Party Repository Trust Roots
----------------------------------
The published tool image installs `gh` and `gum` from their vendors' own yum
repositories.  Both repositories' signing keys are pinned by sha256 in
Containerfile, fetched into /tmp, verified there, and only then installed to
/etc/pki/rpm-gpg — and each .repo file points at that verified local copy with
`gpgkey=file://...`, never at a URL.

Why, in one line: `gpgcheck=1` against a `gpgkey=` URL on the same origin as
the packages proves only that whoever served the package also served the key.
Pinning moves the trust root into this repository, where changing it is a
reviewed commit.  The gh .repo file is written by Containerfile rather than
fetched with `config-manager --from-repofile=`, for the same reason: that file
carries the `gpgkey=` line, so fetching the configuration hands away the choice
of trust root even when every key is otherwise pinned.

Current pins:

  Charm       https://repo.charm.sh/yum/gpg.key
              ED92 7B38 BE98 1E53 CA09  153D 03BB F595 D4DF D35C
              Charmbracelet Inc. <vt100@charm.sh>, expires 2027-07-13

  GitHub CLI  https://cli.github.com/packages/githubcli-archive-keyring.asc
              7F38 BBB5 9D06 4DBC B3D8  4D72 5612 B364 6231 3325   (current)
              2C61 0620 1985 B60E 6C7A  C873 23F3 D4EA 7571 6059   (expired
              2026-09-05, still bundled — a keyring holding a retired key
              alongside its replacement is normal during a rotation)

Action required: when either vendor rotates or re-publishes its key, the
sha256 stops matching and the image build fails with a checksum error.  That is
the intended failure mode — a trust root must not change quietly — but it is
not self-service.  maintenance_audit.py --check-action-updates checks these
pins against upstream weekly and reports a *mismatch as an advisory*, so the
rotation is normally noticed before it breaks a build.

To re-pin, verify identity before writing anything down.  A new digest is
never a rubber-stamp update: the digest only says the file changed, and the
fingerprint is the thing that says it is still the right key.

    curl -fsSL -o /tmp/key https://repo.charm.sh/yum/gpg.key
    gpg --show-keys --with-fingerprint /tmp/key     # compare to the list above
    sha256sum /tmp/key                              # the new pin

If the fingerprint is unchanged, the key was merely re-armored and the new
sha256 can go straight into Containerfile.  If the fingerprint changed, the
vendor rotated: confirm the new fingerprint against an announcement from the
vendor — not against the same host that just served you the key — before
updating both the digest and the fingerprint recorded here and in
Containerfile's comment.

Two things deliberately NOT done here, both from #268 and both still open:
the Fedora base image is a tag rather than a digest (digest-pinning it needs
refresh automation first, or it becomes a stale pin, which is its own hazard),
and the image publishes no SBOM or provenance attestation.  The RPM versions
themselves are deliberately not frozen — security updates are the point of the
nightly rebuild.

tests/test_workflow_dependencies.py holds the offline half of this: every
download in Containerfile has a digest recorded against its destination path,
every recorded digest is actually checked, and no key or .repo file is fetched
over the network at install time.

Pinned Images Shipped To Generated Repositories
-----------------------------------------------
Two container images are written into every repository the tool creates, and
both are pinned by digest in atomic_image_builder.py, with the repository and
tag kept as separate constants so the weekly audit can resolve the tag and
compare:

  UNIVERSAL_BLUE_BREW_IMAGE   ghcr.io/ublue-os/brew                       (#303)
  BOOTC_IMAGE_BUILDER_IMAGE   quay.io/centos-bootc/bootc-image-builder    (#303)

The first is copied whole into `/` of every generated image that enables
Homebrew and its units are preset to run on first boot.  The second produces
every qcow2 and installer ISO a generated repository publishes -- from
build-disk.yml's BIB_IMAGE and from image-template.env, which the Justfile
dotenv-loads for `just build-qcow2`.  Neither is a `uses:` line or a `curl`
line, so neither pin discipline that already existed could see them.

Every emit site interpolates the constant, and the patchers re-pin an existing
repository on its next update: _patch_brew_block() matches on
`COPY --from=` + `brew` + `/system_files`, patch_disk_builder_image() and
patch_image_template_env() match BIB_IMAGE on its repository and any tag or
digest.  A builder the user swapped for a different repository passes through
untouched.

Action required: maintenance_audit.py --check-action-updates resolves each tag
weekly and reports an *advisory* when it no longer lands on the pin.  A re-pin
is a review, not a bump, and the review differs:

  brew   a new payload can ship files neither tests/test_brew_login_fragments.py
         nor tests/test_brew_setup_staging.py has seen; read what changed in
         /system_files before moving the digest.
  bib    the builder has to keep up with the bootc in the base images the wizard
         offers; a disk build against each is the check.  This is the pin that
         trades a supply-chain risk for a compatibility one, which is why it was
         left for a maintainer's decision in #304 and made in the follow-up.

To find the current digest, ask the registry the way the audit does -- a HEAD
whose Accept includes the OCI image index type, because ghcr.io serves the
brew payload as an index and answers a request that does not accept one with a
converted single-platform manifest whose digest is not what `COPY --from=`
resolves:

    python3 -c 'import maintenance_audit as m; print(m.resolve_registry_tag_digest("quay.io", "centos-bootc/bootc-image-builder", "latest"))'

resolve_registry_tag_digest() follows the registry's WWW-Authenticate
challenge rather than assuming a token endpoint: ghcr.io refuses an anonymous
read and names its endpoint, quay.io answers outright and keeps its endpoint
at a different path.  The next registry a pin lands on gets the same treatment
without a special case.
OIDC Token Scope on Generated Builds
------------------------------------
The Containerfile-method workflows are generated without `id-token: write`,
and this is a deliberate divergence from the bundled snapshots, which do
declare it.  strip_permission_entries() removes it in patch_container_workflow
and patch_container_disk_workflow; generate_container_workflow simply does not
emit it.  The snapshots themselves are NOT edited — template_snapshots/ is a
pinned upstream copy — so the drift is in the patchers, where the snapshot
refresh will not silently undo it.

Why it can go: signing on this path is key-based, not keyless.  The workflow
runs `cosign sign --key env://COSIGN_PRIVATE_KEY` with COSIGN_EXPERIMENTAL
explicitly false, and none of the actions it uses asks GitHub for an OIDC
token.  Checked at the pinned SHAs of actions/checkout,
ublue-os/remove-unwanted-software, extractions/setup-just,
docker/login-action, sigstore/cosign-installer, actions/upload-artifact and
osbuild/bootc-image-builder-action: several bundle @actions/core, which
*exports* getIDToken, but none of them calls it.

Why it matters: one job serves pull_request, push and schedule alike, and on a
pull_request event the workflow file comes from the pull request's own head.
Every scope the job declares is therefore a scope a proposed change can spend.
Fork pull requests already get a read-only token from GitHub regardless, so
what this removes is the same-repo-branch case — defence in depth, not a
demonstrated exploit.

The BlueBuild method KEEPS `id-token: write`.  blue-build/github-action hands
the recipe to the BlueBuild CLI, which does support keyless cosign signing, so
there is a plausible consumer there and removing it needs evidence this change
does not have.

Action required: restore `id-token: write` — by dropping "id-token" from
UNUSED_WORKFLOW_PERMISSIONS in atomic_image_builder.py — if the Containerfile
path ever adopts keyless signing, build provenance / artifact attestation
(actions/attest-build-provenance), or registry login by OIDC rather than by
password.  Any of those needs the token, and the failure mode is a red run at
signing time, not a silently unsigned image.  A snapshot refresh that adds
such a step upstream will not trip anything automatically: the round-trip
tests in tests/test_atomic_image_builder.py assert the scope is absent, so
they will keep passing while the new step fails at runtime.  Re-read the
snapshot's steps when refreshing it.


Containerfile-Method Image Identity: image-template.env
--------------------------------------------------------
Since the ublue-os/image-template "rewrite in just" refresh (revision
a18ae9b5), the bundled Containerfile-method Justfile no longer takes an inline
IMAGE_NAME default (env("IMAGE_NAME", "...")). It instead dotenv-loads
image-template.env and reads IMAGE_NAME, REPO_ORGANIZATION, and IMAGE_DESC from
there via env_var(...), which has no fallback if the key is missing.

patch_container_justfile() silently no-ops on this newer Justfile shape by
design (see the section above). The repo name, GitHub owner, and description
are instead wired in by patch_image_template_env(), which rewrites only those
three lines in image-template.env and leaves everything else untouched.

A missing image-template.env is restored from the bundled snapshot only when
the repo's Justfile actually references it (the restore is keyed on the
literal string "image-template.env" appearing in the Justfile text). This is
what keeps older-shape repos — whose Justfile never dotenv-loads the file —
from gaining an inert copy of it on update, while still repairing newer-shape
repos that lost only the env file.

If a future upstream refresh renames these fields, reformats the file (e.g.
switching quoting style), or moves description/org into some other file
again, patch_image_template_env()'s regexes will silently stop matching and
every newly generated repo will publish under the upstream placeholder name
("image-template") instead of the user's chosen repo name. There is currently
no automated check for this beyond the test suite's golden-style coverage
(test_write_project_files_restores_missing_justfile_and_env_from_snapshot and
the patch_image_template_env unit tests) — treat a template refresh that
touches image-template.env or the Justfile's dotenv lines as a signal to
manually verify a generated repo's image-template.env has the right values.

Scan Override: AIB_RPM_OSTREE_STATUS_FILE
------------------------------------------
scan_os() normally invokes `rpm-ostree status --json` directly on the host. That
does not work from inside a container, since the client talks to the host's
rpm-ostreed over the system D-Bus, which the container does not have access to.

When AIB_RPM_OSTREE_STATUS_FILE is set, scan_os() reads that path's contents as
the `rpm-ostree status --json` output instead of invoking rpm-ostree at all (the
command_exists("rpm-ostree") check is skipped too, since nothing is invoked). A
missing or unreadable file, or a file whose contents are not valid JSON, produces
the same "Failed to read rpm-ostree status." error path as a real invocation
failure would.

The container wrapper (contrib/aib) is the only intended consumer: it captures
`rpm-ostree status --json` on the host, mounts the result read-only into the
container, and points this variable at the in-container path. This variable is
not documented in the beginner-facing README; it is an integration detail of the
container distribution, not a user-facing setting.

Local Build Disable: AIB_DISABLE_LOCAL_BUILD
--------------------------------------------
When AIB_DISABLE_LOCAL_BUILD is set (to any non-empty value), the "Test build
locally (podman)" option in test_build_locally() short-circuits with a clean
"not available in this environment" message instead of rendering the project
and invoking podman.

The container image (Containerfile) sets this. Inside the image, podman is
present only as a transitive dependency of rpm-ostree (rpm-ostree -> bootc ->
podman), so command_exists("podman") is true and the tool would otherwise
attempt a nested build, which is not supported in the container and fails.
The env var makes it degrade cleanly instead. Like AIB_RPM_OSTREE_STATUS_FILE,
this is an integration detail of the container distribution, not a
user-facing setting, and is deliberately not documented in the README as a
knob (its effect is described there as a limitation of running in a
container).

BlueBuild Local Test Build: BLUEBUILD_CLI_INSTALLER_IMAGE
---------------------------------------------------------
A BlueBuild local test build (render_bluebuild_containerfile) is the same two
steps the BlueBuild GitHub action performs, with the same tooling:

1. `podman create ghcr.io/blue-build/cli@<BLUEBUILD_CLI_INSTALLER_IMAGE_DIGEST>`,
   then `podman cp <id>:/out/bluebuild` into a temporary directory of its
   own (not the build context, where a COPY could pick it up). This is how
   blue-build/github-action's "Install BlueBuild" step and BlueBuild's own
   install.sh obtain the binary, by the `v0.9-installer` tag. It needs no
   host bluebuild install and does not run the CLI inside the tool
   container, which would be the nested build AIB_DISABLE_LOCAL_BUILD exists
   to refuse.
2. `bluebuild generate --output Containerfile --registry ghcr.io
   --registry-namespace <owner> recipes/recipe.yml`, run in the build
   context. This only reads the registry (base image digest and OS version)
   and the recipe schema, and extracts the CLI's build scripts into
   `.bluebuild-scripts_<sha>/` next to the Containerfile, which the rendered
   Containerfile bind-mounts by relative path. The CLI's driver setup panics
   without docker >= 23 or podman >= 4 on PATH even for `generate`; podman is
   already this feature's prerequisite, so that is not a new one.

The rest is the Containerfile path's `podman build -t <tag> <context>`.

The image is pinned by digest (BLUEBUILD_CLI_INSTALLER_IMAGE_REPO / _TAG /
_DIGEST, the same triplet as the Homebrew payload and bootc-image-builder),
because the binary copied out of it runs on the host as the user, with the
user's files and credentials in reach; a tag anyone with push access to
ghcr.io/blue-build/cli can repoint is not something to execute on that basis.
The tag kept beside the digest is the floating one the pinned
blue-build/github-action installs by default (CLI_VERSION_TAG in its
"Determine Vars" step, "v0.9" at v1.12). The cost of the pin is parity: CI
pulls the tag and moves with it, the local build stays until re-pinned, so a
local build can render with a CLI a step behind CI's. maintenance_audit.py's
weekly run (audit_bluebuild_cli_image_pin) advises when the tag no longer
resolves to the pinned digest. To re-pin: resolve the tag
(`skopeo inspect --raw docker://ghcr.io/blue-build/cli:v0.9-installer | sha256sum`,
or maintenance_audit.resolve_registry_tag_digest), run a local BlueBuild test
build of the wizard's recipe with the new digest, then update
BLUEBUILD_CLI_INSTALLER_IMAGE_DIGEST. When ACTION_PINS["blue-build/github-action"]
changes, re-read the action's default and update
BLUEBUILD_CLI_INSTALLER_IMAGE_TAG with it before re-pinning the digest.

cosign.pub: the recipe's signing module exits 1 unless the CLI copied a public
key into /etc/pki/containers, and the CLI copies it from `cosign.pub` at the
context root (stage-keys in the rendered Containerfile). The update menu hands
its repo clone to test_build_locally so the repo's real key is used; on the
create path the key does not exist yet, so LOCAL_BUILD_PLACEHOLDER_COSIGN_PUB
is written instead. Nothing at build time parses the key, so a marked
placeholder builds the same image layers a real key would; the dryrun image
is never pushed.

Rechunk Step Naming (Chunkah)
-----------------------------
patch_container_rechunk_step() swaps the bundled workflow's rpm-ostree rechunk
step for Chunkah by matching the exact step name "Rechunk with rpm-ostree" and
the recipe invocation via RECHUNK_RECIPE_RE. Both are upstream's literal text,
not a stable API. If a future template refresh renames this step or changes how
it invokes the Justfile's rechunk recipes, this patcher will silently no-op (by
design, matching every other patcher in this file) and generated workflows will
keep rechunking with rpm-ostree instead of Chunkah.
test_patch_container_rechunk_step_is_idempotent and the assertions in
test_patch_container_workflow_matches_current_upstream_snapshot_shape catch
this today only because they run against the real bundled snapshot — if that
snapshot's step text ever drifts, re-check those tests still assert something
meaningful rather than trivially passing on a no-op.

This already happened once, and it is the reason RECHUNK_RECIPE_RE matches two
shapes instead of one literal. Upstream revision b9783f6 made the whole CI
pipeline rootless, rewriting every "sudo -E $(command -v just) X" invocation to
a bare "just X". The old single-literal matcher would not have no-oped
harmlessly: the step-name match still fired, so the step would have been
renamed to "Rechunk with Chunkah" while its command still called
ostree-rechunk. Existing managed repositories are patched in place on update
rather than replaced from the snapshot, so they still carry the pre-rootless
spelling and both must keep matching indefinitely. The same applies to the
stale-comment strip, which is why STALE_CHUNKAH_COMMENT_BLOCKS carries both
spellings of that block. Prefer assertions on the recipe name (rechunk /
ostree-rechunk) over the full invocation when writing tests here, so they keep
testing something real across a sudo-style change.

The same function also strips upstream's trailing "if you are feeling
adventurous, use the new distro agnostic rechunker" comment block once the
active step above it has been switched to Chunkah — left in place, it reads
as self-contradictory (a live Chunkah step immediately followed by comment
text suggesting you switch to Chunkah, plus a now-redundant commented copy of
that same step). Matched on upstream's exact literal text, same no-op-on-
drift convention as everything else here. Found via live use: a real
generated repo (not a test) showed the leftover block and it was genuinely
confusing to read, even though the build itself was unaffected — the active
step was already correct.

Signing Guard: A Boolean At Job Level, Never The Key
----------------------------------------------------
The generated Containerfile workflow gates its two cosign steps on
`env.SIGNING_ENABLED == 'true'`, and the job-level env holds

    SIGNING_ENABLED: ${{ secrets.SIGNING_SECRET != '' }}

The guard has to read a job-level env var because the `secrets` context is not
available in a step-level `if:` -- actionlint will tell you so. What it does
not have to read is the key. Job-level env is set for every step in the job,
`uses:` steps included, so the earlier shape (COSIGN_PRIVATE_KEY and
COSIGN_PASSWORD at job level) handed the signing key to actions/checkout,
remove-unwanted-software, setup-just, login-action and cosign-installer, none
of which want it. See #255. The vendored snapshot never did this; the widening
was ours.

Two things will break signing if they are changed independently, and both fail
in ways that are quiet rather than loud:

- The signing step needs COSIGN_PASSWORD in its *own* env. It used to inherit
  it from the job. add_signing_step_password() puts it there, keyed on the
  step's own COSIGN_PRIVATE_KEY line; if a snapshot refresh moves or renames
  that line the patcher no-ops and cosign cannot decrypt the key -- a failure
  that first appears on someone else's push, not here.

- Existing repositories carry `&& env.COSIGN_PRIVATE_KEY != ''` in both
  conditions. LEGACY_SIGN_CONDITION strips it. Left in place it would test a
  job-level variable that no longer exists, evaluate false forever, and stop
  signing *silently* while the workflow still read as though it signed. That
  is the failure mode patch_cosign_compatibility() already fails closed
  against, arriving from a different direction.

test_existing_repository_migrates_off_the_job_level_key covers the second, and
test_signing_step_carries_its_own_password the first. Both run against text
shaped like what is really on disk in a managed repository, because that is
the input that matters here -- new repositories would look correct either way.

Sign The Digest, Not The Tag
-----------------------------
Both generated paths sign `<registry>/<image>@<digest>`. The bundled snapshot
reads the digest from `podman push --digestfile`; generate_container_workflow()
reads it from the push-to-registry step's `digest` output, which is why that
step carries `id: push-to-ghcr`. publish-image.yml signs this repository's own
image the same way.

The from-scratch path used to loop over `steps.metadata.outputs.tags` and sign
each tag. Every tag that workflow writes is mutable and `latest` is rewritten
by the daily rebuild, so cosign resolving a tag a second time in the signing
step can land on an image the run did not build -- signing that one and leaving
the built one unsigned, while a `cosign verify` against the tag still passes.
One signature on the digest covers every tag pointing at it.

The step fails closed on an empty DIGEST rather than signing `<image>@`,
because the alternative failure is an unsigned image and a green run.
test_generated_workflow_signing_step_signs_the_pushed_digest asserts the step's
body, and the push step's id is asserted next to the registry inputs it must
stay in step with.

Rootless CI and What Existing Repositories Inherit
--------------------------------------------------
Since the b9783f6 snapshot refresh, generated Containerfile-method repositories
run their whole build pipeline rootless: no "sudo -E" wrapper on just or
podman. Upstream made this change because rootfull podman had roughly doubled
build times on GitHub runners (ublue-os/image-template#260). The Chunkah recipe
we enable by default needs no privileges, and "just build" and "just rechunk"
share one rootless container store, so the pipeline stays self-consistent.

This reaches new repositories only. write_container_project_files() patches an
existing repository's Justfile and build.yml in place and restores them from
the bundled snapshot only when the file is missing, which is deliberate: it
preserves user customizations. The consequence is that upstream Justfile
improvements (the rootless invocations, the SOURCE_DATE_EPOCH removal) do not
reach repositories created before the refresh. Carrying a specific upstream fix
to existing repositories takes a targeted patcher, the way
patch_container_rechunk_config_arg() did for the ARG_MAX fix. Decide that per
fix rather than by wholesale-replacing files on update.

Containerfile Workflow Runner Baseline
--------------------------------------
Since the d95b282 snapshot refresh, new Containerfile-method repositories use
the upstream Ubuntu 26.04 GitHub-hosted runners: `ubuntu-26.04` for image
builds, and `ubuntu-26.04` for disk builds since
patch_disk_workflow_platform() fixed the disk workflow to the one architecture
this tool publishes (see the next section; the snapshot still ships the
`ubuntu-26.04` / `ubuntu-26.04-arm` choice, and the patcher resolves it). The
from-scratch generate_container_workflow() fallback uses the same image-build
runner so a missing workflow does not silently restore the older Ubuntu 24.04
baseline.
At this refresh GitHub lists both Ubuntu 26.04 labels as preview images in the
official actions/runner-images table. actionlint 1.7.12 predates those labels
and reports them as unknown, so verify that warning against GitHub's current
runner table before treating it as a bad snapshot label.

Existing managed repositories keep their current runner labels because their
workflow files are patched in place rather than replaced. Migrating those
repositories would require an explicit, targeted patcher; do not turn a future
snapshot refresh into an automatic runner migration that overwrites a user's
custom runner choice.

Disk Workflow Architecture: Restricted, Not Chosen
--------------------------------------------------
The bundled disk workflow offers an arm64 dispatch option and picks a native
ARM runner for it. The image workflow it builds from publishes one native
x86_64 image -- one job, a plain `just build`, no --platform and no
multi-architecture manifest -- and bootc-image-builder requires the builder and
the bootc image to agree on architecture. Choosing ARM therefore could not
produce a matching OS image, and the pinned action does not synthesize the
missing variant. A multi-architecture *base* image does not make the
customized build on top of it multi-architecture either.

patch_disk_workflow_platform() removes the input rather than relabelling the
runner: it drops the `platform:` dispatch input, resolves the runner ternary to
its own amd64 label (captured from the ternary, so a snapshot refresh that
bumps the runner is followed automatically), drops the ARM-only "Install
dependencies" step, and unconditions the "Maximize build space" step whose
`if:` is now always true. That also removes the separate pull-request defect:
on a PR `inputs.platform` is unset, so the ternary selected the ARM runner
while those two step conditions read the same unset input in opposite
directions.

It recognises exactly the two `if:` conditions upstream ships and no-ops on
anything else, like every patcher here. What makes that safe is
test_generated_disk_workflow_only_offers_the_published_architecture, which
asserts no reference to `inputs.platform` survives in the generated project --
so a third condition from a future refresh fails the suite rather than shipping
a workflow with an expression nothing can resolve.

Offering ARM again is not a runner label away. It needs the image workflow to
build and publish the ARM variant first; only then is the disk side worth
changing back.

remove-unwanted-software Pin Tracks a Branch, Not a Tag
-------------------------------------------------------
Since the 1dd3b65 snapshot refresh, upstream image-template pins
ublue-os/remove-unwanted-software at 695eb75b -- its master HEAD (the merge of
the v10 work), for which no v10 tag exists yet. The ACTION_PINS entry follows
it with the label "master", so the weekly action-pin freshness audit will
advise when that branch moves, the same way the osbuild/bootc-image-builder
"main"-labelled pins already behave. The older ACTION_REF_PINS entries that
label the same SHA "v8" are deliberate history (upstream once moved the v8 tag
backwards; see the comment in maintenance_audit.py's describe_pin_drift) and
must not be "corrected" to match. They exist for the audit, not for the
comment: pin_action_uses_line() writes ACTION_PINS' label whenever the SHA it
lands on is ACTION_PINS' SHA, so a workflow line at 695eb75b reads "# master"
however it arrived there. Before that rule (#349) the ref table's "v8" won,
and every repository generated from scratch had the generator's "# master"
rewritten to "# v8" on its first update, with no upstream change behind it.

Rechunk Recipe ARG_MAX Fix (CHUNKAH_CONFIG_STR)
------------------------------------------------
Older managed repositories may still have a `rechunk` recipe that does:

    export CHUNKAH_CONFIG_STR=$(podman inspect "${target_image}")
    podman run --rm ... -e CHUNKAH_CONFIG_STR quay.io/coreos/chunkah:latest ...

For a base image that is itself already chunked — which in practice means
most Universal Blue images (Bazzite, Aurora, Bluefin, and their DX variants
are all built via a chunked pipeline upstream) — the `podman inspect` output's
layer-history array is large enough that exporting it as a shell environment
variable exceeds the kernel's argument/environment size limit. Every
subsequent podman invocation in that shell then fails outright with
"/usr/bin/podman: Argument list too long" (exit 126), before chunkah ever
runs. Fedora Atomic base images (Silverblue, Kinoite, etc.) are not
pre-chunked upstream, so this specific combination — Containerfile method +
a Universal Blue base — was the one untested path when Chunkah rechunking was
turned on by default; discovered via a real demo build against
ghcr.io/ublue-os/bluefin:stable.

patch_container_rechunk_config_arg() (called from patch_container_justfile(),
so it applies to existing repositories on their next update) rewrites that
legacy shape to write the inspect output to a temp file and pass it to chunkah
via its documented `--config <path>` flag, mounted with the `Z` SELinux relabel
flag. This avoids both the ARG_MAX and SELinux permission failures.

The refreshed bundled template now carries the upstream OCI-directory recipe:
it uses a config temp file, a temporary `*_chunkah_*` output directory, an EXIT
trap for both, and `--output oci:/run/out/chunked`, then pulls and retags the
resulting OCI image. It no longer passes `SOURCE_DATE_EPOCH=0`: upstream
dropped that in image-template 94e9423 because pinning it to the epoch clamps
file mtimes but also discards the package stability data chunkah uses to plan
layers, which costs users delta-update quality (coreos/chunkah#160). The noop
test asserts it stays gone so a future refresh cannot quietly reintroduce it. The upstream revision originally
derived that temporary directory from `${target_image}`. Registry-qualified
image names contain slashes (for example `ghcr.io/acme/image`), which made
`mktemp` interpret parts of the image name as nonexistent parent directories.
The bundled snapshot instead uses the generic local template
`./aib_chunkah_XXXXXX`, and patch_container_rechunk_config_arg() rewrites that
exact vulnerable upstream form in existing managed repositories. The patcher
no-ops on the corrected current shape and remains covered by current-snapshot,
qualified-image, and explicit legacy-fixture tests.

Batched dnf5 Package Lookups (lookup_host_packages)
-----------------------------------------------------
lookup_host_packages() checks every requested package name in a single dnf5
repoquery call instead of one call per package. dnf5's first repoquery
invocation pays a real, sometimes very large (tens of seconds) cost to warm
its metadata cache; every call after that on a warm cache is fast. When the
old code ran one dnf5 process per package in a loop, that warm-up cost was
paid on the first package and only the first package's "Checking package
name" spinner was ever visible for more than a fraction of a second, even
though every package genuinely was being checked correctly. Found by
timestamp-analyzing a real asciinema demo recording: the "tmux" spinner ran
for 46 real seconds (458 rendered frames) while the very next package,
"htop", finished in 0.20s (3 frames) — not a logic bug, but confusing enough
to look like one.

lookup_host_package(package) still exists as a single-package convenience
wrapper around lookup_host_packages([package]); it is the batched call that
actually avoids the per-package dnf5 cost, so callers that check more than
one package at a time (_filter_manual_packages) must call the plural form
directly rather than looping over the singular one.

The dnf5 --qf format string was changed from "%{name}" to "%{name}\n". This
matters only in the batched case: dnf5 concatenates multiple results with no
separator at all when the format string has none (confirmed live: two
results printed back to back as a single unparseable "htoptmux"-style
string), so parsing per-package results out of a multi-package query
requires the explicit newline. search_host_packages() already did this
correctly elsewhere in this file; lookup_host_package() was the one call
site that had been missing it, invisibly, because a single-package query
never has more than one result to separate.

The lookup query is cache-only (dnf5 -C), like the search query. Before #369
it was not, and dnf5 quietly fetched the full repository metadata -- about
160 MB on Fedora -- behind the "Checking package name" spinner whenever the
cache was missing or expired (48 h for fedora, 6 h for updates), while the
search screen on the same empty cache stopped and asked first. Both paths now
treat dnf5's "cache-only enabled but no cache" failure the same way: offer
refresh_package_metadata() once, retry with the offer disabled so a refresh
that produces no usable cache cannot loop, and otherwise carry on. For the
lookup, "carry on" means every name in the batch comes back None -- kept, with
the usual "could not fully check" warning -- rather than blocking entry, and
that None is deliberately not written to package_lookup_cache: declining a
download says nothing about the names, and a refresh accepted later (from
either screen) must be able to check them properly. The batching story above
is unchanged; what the first call used to spend downloading is now the
explicit, consented refresh.

The batch is an exact-name check, and `dnf5 install` accepts more than exact
names (#370). Two specs the generated build.sh installs were rejected as
typos: `vim`, which repoquery prints nothing for because a positional
repoquery argument does not resolve Provides (install resolves it to
vim-enhanced), and `vim-enhanced.x86_64`, for which repoquery prints the bare
name `vim-enhanced`, not string-equal to the spec. The batch cannot say which
argument printed which line, so _resolve_package_spec() re-asks per leftover
spec, on the cache the batch just warmed: `--whatprovides <spec>` first (it is
case-sensitive and every package provides its own name), then a positional
`<spec>` query for NEVRA forms, accepted only when a printed name opens the
spec verbatim. That last condition is what keeps `Vim-Enhanced` rejected:
positional repoquery matches ignoring case (5.4.2.1 prints vim-enhanced for
it), install does not ("No match for argument"). A spec with no ".", "-" or
":" skips the positional query, since it can only be a plain name and
--whatprovides already answered that. Confirmed live against dnf5 5.4.2.1:
vim, vim-enhanced.x86_64, htop-3.4.1 and the virtual `webserver` resolve;
Vim-Enhanced, HTOP, nethock and python3-foo-typo do not. Binaries by bare name
(`dnf5 install <name>` also matches /usr/bin/<name>) are not resolved here; a
user who types one keeps the "not found" message and can enter the package
name instead.

The same lookup checks the Removed Base Packages screen, and there Provides
must stay rejected. The generated build.sh only removes a package after
`rpm -q --quiet "$pkg"` succeeds, and rpm -q matches names and NEVRA forms
only: on a host with vim-enhanced (Provides: vim) installed, `rpm -q --quiet
vim` exits 1 while vim-enhanced.x86_64 and htop-3.4.1 exit 0. Accepting `vim`
as a removal would save it and then skip it at build time with "not
installed in the base image". So lookup_host_packages() takes
resolve_provides: the removal filter passes False, which skips the
--whatprovides step and keeps the positional NEVRA follow-up, and the cache
is keyed by (spec, resolve_provides) so `vim` accepted on the install screen
does not leak into the removal screen. Swapping a Provides for its provider
was not taken: `webserver` has three providers, and the state file would
hold a name the user never typed.

Removal Entry Asks the rpmdb Before the Repos (lookup_removable_host_packages)
------------------------------------------------------------------------------
The removed-package screen used the same `dnf5 repoquery --available` lookup
as the install screen, which asks "is this in an enabled repo?" when the
question is "is this in the base image?". Universal Blue images ship
packages from their own repos (uupd, ublue-os-*, bluefin-*) that are in
neither fedora nor updates, so on a Bluefin host `uupd` was reported as a
typo and dropped, even though the generated build.sh would have removed it
fine (#371). lookup_removable_host_packages() now asks
lookup_installed_host_packages() first -- one `rpm -q` over the batch -- and
sends only the names rpm did not confirm on to the repo query, with
resolve_provides=False for the reason given above. Installed is final; not-installed and could-not-check both fall through, because the
host may have overridden the package away already, or be running a
different base than the one being built, and the repo answer for those is
the one the screen always gave. Nothing that was accepted before is rejected
now.

Two details of the rpm call are load-bearing. It is `rpm -q`, not `dnf5
repoquery --installed`: the dnf5 form opens /var/lib/dnf/system-repo.lock
and fails for an unprivileged user (confirmed on Bluefin DX 44). And the
misses are parsed off rpm's own "package <spec> is not installed" stdout
lines rather than by matching the printed %{name} of the hits: rpm accepts
name.arch and name-version specs and prints the bare name for them, so a
hit for vim-enhanced.x86_64 prints "vim-enhanced" and would never match the
spec that was asked. The miss line echoes the spec verbatim. A database rpm
cannot open produces the same exit 1 *and* a "not installed" line per spec,
distinguishable only by the "error:" line on stderr, so that is checked
first and turns the whole batch into "could not check" rather than a
confident typo verdict for every removal.

The rpm results are cached separately (installed_package_lookup_cache) from
the repo results (package_lookup_cache). They answer different questions:
installed-on-the-host is evidence for a removal, not for an install, and the
install screen deliberately never consults it.

Chunkah Config and Output Cleanup: trap, not trailing rm commands
---------------------------------------------------------------
The current recipe registers `trap 'rm -f "${CHUNKAH_CONFIG_FILE}"; rm -rf
"${CHUNKAH_OUTPUT_DIR}"' EXIT` immediately after creating both temporary
resources. The recipe runs under `set -e`: trailing cleanup commands only run
on success, so a failed Chunkah invocation could otherwise leave the inspect
data or OCI output directory behind. The EXIT trap guarantees cleanup on every
exit path. The legacy patcher uses the same trap for the config file.

The original fix (see above) shipped with the bare trailing `rm -f` and this
exact gap; it was flagged by a maintainer (renner0e) reviewing the upstream
issue filed for the ARG_MAX fix, and confirmed here as a real, reproducible
leak, not just a theoretical one:
test_patch_container_rechunk_config_arg_temp_file_survives_failed_run_without_trap
runs a stripped-down bare-rm-f version of the recipe body under a real bash
with a podman stub that fails, and shows the temp file surviving.
test_patch_container_rechunk_config_arg_cleans_up_temp_file_on_failure runs
the actual patched recipe body (extracted from patch_container_rechunk_config_arg's
real output, not a hand-copied duplicate) the same way and shows the trap
does clean it up. Both tests require a real bash and are skipped if one
isn't available.

Brew Payload Login-Shell Fragments: a hard-coded list plus a build-time sweep
-----------------------------------------------------------------------------
BREW_LOGIN_FRAGMENTS in atomic_image_builder.py names three files by path:

  /etc/profile.d/brew.sh
  /etc/profile.d/brew-bash-completion.sh
  /usr/share/fish/vendor_conf.d/ublue-brew.fish

They are not written by this repository. They arrive in every generated image
through `COPY --from=ghcr.io/ublue-os/brew:latest /system_files /`, which the
Containerfile generator, the Containerfile patcher and the BlueBuild recipe's
containerfile module all emit when brew_enabled is on. Each one executes code
out of /home/linuxbrew/.linuxbrew, and brew-setup.service ends with
`chown -R 1000:1000 /home/linuxbrew`, so on a booted machine that prefix is
owned by the desktop user. /etc/profile.d and the fish vendor directory are
read by every login shell, root's included, which makes each fragment UID 1000
choosing what root executes.

brew_login_fragment_run_lines() emits the step that removes them, installs
/etc/profile.d/brew-path.sh (PATH only, guarded by `test -O`, executes nothing
from the prefix) and then greps the login-shell directories, failing the build
if anything else there still mentions brew.

The list is this digest's inventory; the sweep is what covers the next one.
That split is deliberate, because the reference is a mutable tag on an image
this repository does not build: a later digest can add a fourth fragment
without a single tracked file changing here, and no static check in this tree
can see it. Removing the sweep to "simplify" the step removes the only part
that is not already out of date.

Action required: none on a schedule. When a build starts failing with
"unguarded Homebrew shell integration from the brew payload", the payload has
grown a fragment. Read it, and either add its path to BREW_LOGIN_FRAGMENTS or,
if it turns out to be safe, exclude it explicitly in the sweep -- do not widen
the grep. tests/test_brew_login_fragments.py executes the step against fixture
trees, so a change to either half is exercised rather than pattern-matched.
