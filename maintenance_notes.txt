Maintenance Notes
=================

Fedora Atomic Fallback Tag
--------------------------
FEDORA_ATOMIC_FALLBACK_TAG in atomic_image_builder.py is the default Fedora
version used for Fedora Atomic base images (Silverblue, Kinoite, etc.) when the
tool cannot detect the host's Fedora version.

The detection works like this:
- On a Fedora system, the tool reads VERSION_ID from /etc/os-release and uses
  that directly.  When the user upgrades to a new Fedora release, the tool
  picks it up automatically.
- On non-Fedora systems (Ubuntu, macOS, containers without os-release), the
  tool falls back to FEDORA_ATOMIC_FALLBACK_TAG.

Universal Blue images are unaffected — they use :stable, which floats
automatically.

Action required: when a Fedora release goes EOL, bump FEDORA_ATOMIC_FALLBACK_TAG
to the current stable Fedora version.  This is a one-line change.  The
maintenance audit (maintenance_audit.py) is the right place to add a check for
this if desired.

Workflow Patcher Indentation Sensitivity
----------------------------------------
patch_workflow_signing_steps, ensure_workflow_job_env_entries, and the per-line
patch_container_workflow / patch_bluebuild_workflow helpers in
atomic_image_builder.py all depend on the exact indentation used by the bundled
template snapshots (2-space step items; 4-space env:/steps: anchors; 6-space
job-env entries).  ensure_workflow_job_env_entries silently returns the text
unchanged when its anchor regex does not match.

maintenance_audit.py currently validates action pin coverage but does not run
the patchers against the snapshots.  When refreshing a template snapshot, run
the test suite — the golden-file patcher tests in
tests/test_atomic_image_builder.py cover the current shape.  Add a round-trip
audit here if upstream ever changes the indentation style; the silent no-op
failure mode is hard to notice otherwise.

Containerfile-Method Image Identity: image-template.env
--------------------------------------------------------
Since the ublue-os/image-template "rewrite in just" refresh (revision
f9a9e4f8), the bundled Containerfile-method Justfile no longer takes an inline
IMAGE_NAME default (env("IMAGE_NAME", "...")). It instead dotenv-loads
image-template.env and reads IMAGE_NAME, REPO_ORGANIZATION, and IMAGE_DESC from
there via env_var(...), which has no fallback if the key is missing.

patch_container_justfile() silently no-ops on this newer Justfile shape by
design (see the section above). The repo name, GitHub owner, and description
are instead wired in by patch_image_template_env(), which rewrites only those
three lines in image-template.env and leaves everything else untouched.

A missing image-template.env is restored from the bundled snapshot only when
the repo's Justfile actually references it (the restore is keyed on the
literal string "image-template.env" appearing in the Justfile text). This is
what keeps older-shape repos — whose Justfile never dotenv-loads the file —
from gaining an inert copy of it on update, while still repairing newer-shape
repos that lost only the env file.

If a future upstream refresh renames these fields, reformats the file (e.g.
switching quoting style), or moves description/org into some other file
again, patch_image_template_env()'s regexes will silently stop matching and
every newly generated repo will publish under the upstream placeholder name
("image-template") instead of the user's chosen repo name. There is currently
no automated check for this beyond the test suite's golden-style coverage
(test_write_project_files_restores_missing_justfile_and_env_from_snapshot and
the patch_image_template_env unit tests) — treat a template refresh that
touches image-template.env or the Justfile's dotenv lines as a signal to
manually verify a generated repo's image-template.env has the right values.

Scan Override: AIB_RPM_OSTREE_STATUS_FILE
------------------------------------------
scan_os() normally invokes `rpm-ostree status --json` directly on the host. That
does not work from inside a container, since the client talks to the host's
rpm-ostreed over the system D-Bus, which the container does not have access to.

When AIB_RPM_OSTREE_STATUS_FILE is set, scan_os() reads that path's contents as
the `rpm-ostree status --json` output instead of invoking rpm-ostree at all (the
command_exists("rpm-ostree") check is skipped too, since nothing is invoked). A
missing or unreadable file, or a file whose contents are not valid JSON, produces
the same "Failed to read rpm-ostree status." error path as a real invocation
failure would.

The container wrapper (contrib/aib) is the only intended consumer: it captures
`rpm-ostree status --json` on the host, mounts the result read-only into the
container, and points this variable at the in-container path. This variable is
not documented in the beginner-facing README; it is an integration detail of the
container distribution, not a user-facing setting.

Local Build Disable: AIB_DISABLE_LOCAL_BUILD
--------------------------------------------
When AIB_DISABLE_LOCAL_BUILD is set (to any non-empty value), the "Test build
locally (podman)" option in test_build_locally() short-circuits with a clean
"not available in this environment" message instead of rendering the project
and invoking podman.

The container image (Containerfile) sets this. Inside the image, podman is
present only as a transitive dependency of rpm-ostree (rpm-ostree -> bootc ->
podman), so command_exists("podman") is true and the tool would otherwise
attempt a nested build, which is not supported in the container and fails.
The env var makes it degrade cleanly instead. Like AIB_RPM_OSTREE_STATUS_FILE,
this is an integration detail of the container distribution, not a
user-facing setting, and is deliberately not documented in the README as a
knob (its effect is described there as a limitation of running in a
container).

Rechunk Step Naming (Chunkah)
-----------------------------
patch_container_rechunk_step() swaps the bundled workflow's rpm-ostree rechunk
step for Chunkah by matching the exact step name "Rechunk with rpm-ostree" and
the exact substring "command -v just) ostree-rechunk". Both are upstream's
current literal text, not a stable API. If a future template refresh renames
this step or changes how it invokes the Justfile's rechunk recipes, this
patcher will silently no-op (by design, matching every other patcher in this
file) and generated workflows will keep rechunking with rpm-ostree instead of
Chunkah. test_patch_container_rechunk_step_is_idempotent and the assertions in
test_patch_container_workflow_matches_current_upstream_snapshot_shape catch
this today only because they run against the real bundled snapshot — if that
snapshot's step text ever drifts, re-check those tests still assert something
meaningful rather than trivially passing on a no-op.

The same function also strips upstream's trailing "if you are feeling
adventurous, use the new distro agnostic rechunker" comment block once the
active step above it has been switched to Chunkah — left in place, it reads
as self-contradictory (a live Chunkah step immediately followed by comment
text suggesting you switch to Chunkah, plus a now-redundant commented copy of
that same step). Matched on upstream's exact literal text, same no-op-on-
drift convention as everything else here. Found via live use: a real
generated repo (not a test) showed the leftover block and it was genuinely
confusing to read, even though the build itself was unaffected — the active
step was already correct.

Rechunk Recipe ARG_MAX Fix (CHUNKAH_CONFIG_STR)
------------------------------------------------
The bundled Justfile's `rechunk` recipe (upstream, unpatched) does:

    export CHUNKAH_CONFIG_STR=$(podman inspect "${target_image}")
    podman run --rm ... -e CHUNKAH_CONFIG_STR quay.io/coreos/chunkah:latest ...

For a base image that is itself already chunked — which in practice means
most Universal Blue images (Bazzite, Aurora, Bluefin, and their DX variants
are all built via a chunked pipeline upstream) — the `podman inspect` output's
layer-history array is large enough that exporting it as a shell environment
variable exceeds the kernel's argument/environment size limit. Every
subsequent podman invocation in that shell then fails outright with
"/usr/bin/podman: Argument list too long" (exit 126), before chunkah ever
runs. Fedora Atomic base images (Silverblue, Kinoite, etc.) are not
pre-chunked upstream, so this specific combination — Containerfile method +
a Universal Blue base — was the one untested path when Chunkah rechunking was
turned on by default; discovered via a real demo build against
ghcr.io/ublue-os/bluefin:stable.

patch_container_rechunk_config_arg() (called from patch_container_justfile(),
so it applies to every new repo and to every existing repo's next update)
rewrites the recipe to write the inspect output to a temp file and pass it to
chunkah via its documented `--config <path>` flag (mounted into the container)
instead of the environment variable. This has no size limit. The mount uses
the `Z` SELinux relabel flag — without it, chunkah fails a second, different
way ("Permission denied" reading the mounted file) on SELinux-enforcing hosts
such as GitHub's ubuntu-24.04 runners and any Fedora/bootc box. Both failure
modes, and the fix, were verified by actually running the unpatched and
patched recipes against a real pulled ghcr.io/ublue-os/bluefin:stable image,
not just asserted in unit tests.

Matched on upstream's exact current literal text, same as every other patcher
in this file: if a future template refresh changes the rechunk recipe's
shape, this silently no-ops and generated/updated repos go back to hitting
the ARG_MAX crash on Universal Blue bases.
test_patch_container_rechunk_config_arg_fixes_real_snapshot catches this only
because it runs against the real bundled snapshot.

This was also reported upstream to ublue-os/image-template so the fix can
land there directly and this patcher can eventually be retired.
